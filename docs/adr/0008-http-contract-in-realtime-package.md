# 0008. HTTP 계약도 packages/realtime의 zod 스키마로 정의하고 파싱을 한곳에 모은다

- **상태**: Accepted
- **날짜**: 2026-09-01
- **관련**: [0003](./0003-sse-for-broadcast-ws-for-conversation.md), [0004](./0004-internal-packages-source-only.md),
  `docs/specs/S01`, `docs/specs/S13`, `docs/specs/S14`

## 맥락 (Context)

실시간 메시지(SSE/WS)는 이미 `packages/realtime`의 discriminated union으로 정의하고
그 안에서만 파싱한다. 반면 HTTP 응답은 규칙 밖에 있었다 — `HomeScreen`이
`await res.json()` 결과를 `SessionSummary[]`로 캐스팅하고, 화면 파일마다 응답 모양을
인터페이스로 다시 적었다. 서버가 필드를 바꿔도 컴파일은 통과하고 런타임에서야 깨진다.

S01·S13·S14가 HTTP 엔드포인트를 8개 더 늘리고(방 발급/조회, 세션 생성·제어·상태,
관리자 현황·설정), 그중 관리자 현황은 **대화 내용이 실리면 안 된다**는 개인정보
제약까지 있다. 캐스팅으로 버티면 계약이 세 곳(서버 코드, 화면 인터페이스, 명세)에
흩어진다.

## 결정 (Decision)

HTTP 요청·응답 계약도 `packages/realtime/src/http.ts`에 zod 스키마로 정의하고,
`@thegame/realtime/http`로 노출한다. 서버는 요청 본문 검증에, 클라이언트는 응답
해석에 같은 스키마를 쓴다. 화면 코드는 `res.json()` 결과를 캐스팅하지 않고
`decodeX(value)`를 거친다 — 스트림의 `parseX(raw)`와 짝을 이루되, 이미 값이 된
입력을 받으므로 결과 타입은 `DecodeResult<T>`로 분리한다.

관리자 현황 행(`adminRoomSchema`)은 `z.strictObject`로 정의해 명세에 없는 필드가
붙으면 파싱이 실패하게 한다.

## 검토한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 탈락 사유 |
|------|------|------|-----------|
| 지금처럼 화면에서 캐스팅 | 코드가 짧다 | 계약 위반이 런타임까지 감춰짐, 응답 모양이 화면마다 중복 정의 | 무음 실패 금지 규칙과 정면 충돌 |
| 서버에만 zod, 클라이언트는 타입만 공유 | 서버 입력 검증은 확보 | 응답이 바뀌어도 클라이언트는 조용히 undefined를 그림 | 계약이 한 방향으로만 보장돼 절반의 이득 |
| OpenAPI 스키마 + 코드 생성 | 표준, 문서 자동화 | 생성 파이프라인·빌드 단계 추가, 소스 직접 참조(ADR-0004)와 어긋남 | 엔드포인트 10여 개 규모에 과함 |

## 결과 (Consequences)

- (+) 서버 응답과 화면의 기대가 한 파일에서 갈라진다 — 계약이 바뀌면 양쪽 테스트가
  동시에 깨진다(실제로 `state` 없는 예전 세션 목록은 파싱 실패로 잡힌다)
- (+) "대화 내용을 관리자에게 보내지 않는다"는 정책이 문서가 아니라 strict 스키마로
  강제된다 — 서버가 필드를 늘리면 계약 테스트가 먼저 실패한다
- (+) 목 서버가 요청 본문 검증에 같은 스키마를 써서 검증 규칙이 중복되지 않는다
- (−) 응답 필드를 하나 늘리는 데도 realtime 패키지를 고쳐야 한다 — 서버만 고치면
  끝나던 변경의 비용이 올라간다
- (−) strict 스키마는 서버가 필드를 **추가**할 때도 클라이언트를 깨뜨린다.
  관리자 현황처럼 "새지 않는 것"이 요구사항인 응답에만 제한적으로 쓴다
- (−) zod 스키마가 런타임 코드라 클라이언트 번들이 조금 커진다(이미 실시간
  이벤트 파싱에 zod를 싣고 있어 증분은 작다)
