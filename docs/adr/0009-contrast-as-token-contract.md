# 0009. 대비 기준을 토큰 계약으로 고정하고, 컨트롤 경계를 장식용 선과 분리한다

- **상태**: Accepted
- **날짜**: 2026-09-01
- **관련**: [S06 접근성 패스](../specs/S06-accessibility.md), [S04 스테이지 모드](../specs/S04-stage-mode.md)의 다크 대비 실측 표

## 맥락 (Context)

S06은 "라이트·다크 전 조합이 WCAG AA를 통과한다"를 완성 기준으로 두고, 검증 장치로
`packages/tokens`의 대비 유닛 테스트를 요구한다. 실제로 붙이려니 두 가지가 걸렸다.

1. **"전 조합"을 문자 그대로 곱집합으로 돌리면 테스트가 무의미해진다.** 시맨틱 토큰
   16개의 곱집합은 240쌍인데, 그중 화면에 같이 나오는 건 30쌍이 안 된다.
   `danger` 위의 `success` 같은 조합까지 빨개지면 아무도 안 보게 되고, 통과시키려면
   팔레트를 회색으로 만들어야 한다.
2. **`border`가 두 가지 일을 하고 있었다.** 헤더·푸터·카드의 hairline 구분선과
   입력·칩의 테두리가 같은 토큰(`neutral[200]` / 라이트 1.29:1)을 쓴다.
   WCAG 1.4.11은 "순수 장식"을 명시적으로 제외하지만 **UI 컴포넌트의 경계**는
   3:1을 요구한다. 하나의 토큰으로는 둘 중 하나를 반드시 어긴다 — 3:1로 올리면
   장식용 구분선이 굵고 탁해지고, 지금 값을 두면 입력 칸의 경계가 기준 미달이다.
   (S04가 "라이트도 같은 값이니 의도된 장식으로 보인다"며 S06에 넘긴 항목이다.)

또 상태 톤(`success`/`warning`/`info`)이 라이트·다크에서 **같은 500단**이라,
라이트에서는 너무 밝고(3.1~3.3:1) 다크에서는 너무 어두웠다(`info` 2.62:1).
S04가 `danger`만 다크에서 `red[400]`으로 올려 둔 것과 같은 문제가 나머지에 남아 있었다.

## 결정 (Decision)

1. **검사 대상 조합을 `packages/tokens/src/contrast.ts`에 명시적 목록으로 둔다.**
   `textPairs`/`nonTextPairs`의 각 항목은 `usedAt`(어느 화면에서 쓰는지)을 반드시 갖고,
   제외한 조합은 `excludedPairs`에 **이유와 함께** 남긴다. 화면에 새 조합을 도입하면
   목록에 한 줄을 먼저 추가하는 것이 규칙이다. 곱집합은 돌리지 않는다.
2. **`borderStrong`을 새 시맨틱 토큰으로 추가한다.** `border`는 장식용 hairline 전용으로
   두고(대비 검사 제외), 입력·칩 등 **컨트롤 경계는 `borderStrong`**을 쓰며 3:1로 검사한다.
3. **상태 톤은 모드별로 다른 팔레트 단을 쓴다.** 라이트는 600단, 다크는 400단
   (`green[400]`/`amber[400]`/`blue[400]`을 팔레트에 추가). S04가 `danger`에 한 조치를
   나머지 상태 톤에 일반화한 것이다.
4. **컴포넌트가 만드는 합성 배경(배지의 tone 12% 틴트)은 토큰 테스트의 대상이 아니다.**
   토큰 두 개의 조합이 아니라 컴포넌트의 알파 선택이라, 토큰을 고쳐 맞추면
   상태 톤 전체가 화면 어디서든 과하게 진해진다. 이건 컴포넌트 쪽 과제로 넘긴다
   (아래 "결과" 참고).

## 검토한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 탈락 사유 |
|------|------|------|-----------|
| 곱집합 전수 검사 | 목록 관리가 필요 없다 | 안 쓰는 조합이 대량 실패, 통과시키려면 팔레트를 뭉갠다 | 신호가 죽는다 |
| `border` 하나를 3:1로 올린다 | 토큰이 안 늘어난다 | 헤더·카드 구분선이 4.5:1짜리 회색 선이 된다 | 장식용 선은 1.4.11 제외 대상이라 올릴 근거가 없다 |
| `border`를 그대로 두고 검사에서 뺀다 | 변경 없음 | 입력·칩 경계가 1.29:1로 남는다 — 1.4.11 위반 | 저시력 사용자가 입력 칸의 경계를 못 본다 |
| 배지 틴트를 12%→25%로 올려 토큰을 그대로 둔다 | 토큰 변경 없음 | live-demo 컴포넌트 소유가 아니다(동시 작업 중) | 이번 범위 밖 — 인계 항목으로 남긴다 |
| 상태 톤을 모드 공통으로 두고 중간값을 찾는다 | 토큰이 안 늘어난다 | 라이트 4.5 · 다크 4.5를 동시에 만족하는 값이 없다(배경 명도 차가 15배) | 수학적으로 불가능 |

## 결과 (Consequences)

**얻는 것**

- 토큰 값이 바뀌면 CI가 먼저 깨진다. 실패 메시지에 색·수치·기준이 함께 찍혀,
  "어디를 얼마나 고쳐야 하는지"가 바로 나온다.
- 제외 결정이 코드에 남는다. `excludedPairs`의 이유를 읽지 않고는 조합을 뺄 수 없다.
- 라이트 세트의 미달 13조합, 다크 6조합, 컨트롤 경계 6조합이 한 번에 정리됐다.

**잃는 것**

- **목록 관리 비용**이 생긴다. 새 조합을 화면에 쓰면서 목록에 안 넣으면 검사에서 샌다.
  (`usedAt`을 필수로 만들어 최소한 "왜 넣었는지"는 남게 했지만, 누락은 못 막는다.)
- **화면 색이 눈에 띄게 바뀐다.** 라이트 `primary`가 `teal[600]`→`teal[700]`,
  `textMuted`가 `neutral[500]`→`neutral[600]`이라 브랜드 톤이 한 단 진해졌다.
  product와 live-demo 양쪽에 동시에 적용된다.
- **입력·칩 테두리가 진해진다.** 1.29:1 → 4.48:1. 폼이 이전보다 무겁게 보인다.
  기준(3:1)보다 여유가 크지만, 팔레트의 기존 단(`neutral[500]`)을 쓰기로 해서 생긴 값이다.
- **배지 합성 배경은 여전히 미달로 남는다.** tone을 12%(RN은 `1F` = 12.16%) 알파로 깐
  배경 위의 같은 tone 라벨은, 토큰을 고친 뒤에도 라이트 3.79~4.36:1(상태 톤 4종 전부 미달),
  다크 `surfaceSubtle` 위에서 4.12~4.35:1(neutral·danger·info 미달)이다.
  토큰을 여기 맞추면 상태 톤이 화면 어디서든 과하게 진해지므로,
  RN 접근성 담당(live-demo `ConnectionBadge`/`SessionStateBadge`)과 `packages/ui`의 `Badge`가
  틴트를 올리거나(≈25%) 라벨 색을 배경과 분리해야 한다 — 토큰만으로는 못 고친다.
