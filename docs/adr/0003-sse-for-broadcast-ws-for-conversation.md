# 0003. 학회 자막 스트리밍은 SSE, 병원 대화 통역은 WebSocket을 사용한다

- **상태**: Accepted
- **날짜**: 2026-08-31
- **관련**: [0002](./0002-live-demo-expo-react-native.md)

## 맥락 (Context)

두 실시간 시나리오는 통신 패턴이 다르다.

- **학회 자막**: 서버 → 다수 참석자로의 **단방향 브로드캐스트**. 참석자는 읽기만 한다.
- **병원 대화**: 의료진↔환자 간 **양방향** 메시지 교환. 양쪽 모두 발화를 전송한다.

하나의 기술로 통일할 수도 있으나, JD가 WebSocket과 SSE를 모두 명시하고 있고
실제로도 패턴별 최적 기술이 다르다.

## 결정 (Decision)

- 학회 자막(단방향 다수 수신): **SSE** — 자동 재연결(`Last-Event-ID` 기반 유실 복구)이
  프로토콜에 내장돼 있고, HTTP 인프라(프록시, 압축)를 그대로 활용한다.
- 병원 대화(양방향 1:1): **WebSocket** — 발화 전송과 번역 수신이 한 연결에서
  일어나야 하며, 요청-응답 왕복 없이 낮은 지연으로 교환한다.

## 검토한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 탈락 사유 |
|------|------|------|-----------|
| 전부 WebSocket | 기술 스택 단일화 | 단방향 시나리오에 과잉, 재연결·유실 복구를 직접 구현 | 자막처럼 "읽기 전용 + 유실 복구 중요" 패턴엔 SSE가 구조적으로 단순·견고 |
| 전부 SSE + POST | HTTP만으로 해결 | 발화 전송이 별도 요청, 연결 2개 관리 | 대화형 UX에서 왕복 지연·연결 관리 복잡도 증가 |
| 폴링(long polling) | 구현 최다 단순 | 지연 크고 실시간 UX 불성립 | 실시간 자막 요구사항 미충족 |

## 결과 (Consequences)

- (+) 두 프로토콜의 사용처 판단 기준을 실코드로 증명 (JD 요구사항 직결)
- (+) SSE의 `Last-Event-ID`로 "재연결 시 놓친 자막 복구"를 데모 기능으로 시연 가능
- (−) 목 서버가 두 프로토콜을 모두 구현해야 함 → `apps/mock-server`에서 공통
  스크립트 재생 로직을 공유하고 전송 계층만 분리
- (−) RN에는 네이티브 `EventSource`가 없음 → 폴리필(`react-native-sse` 등) 필요.
  전송 계층을 `packages/realtime`으로 추상화해 플랫폼별 구현을 주입한다
