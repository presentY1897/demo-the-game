# 0001. pnpm workspace 기반 모노레포로 프로젝트를 구성한다

- **상태**: Accepted
- **날짜**: 2026-08-31

## 맥락 (Context)

기업 홈페이지(A), 제품 홈페이지(B), 실시간 번역 라이브 데모(C)와 이들이 공유하는
디자인 시스템·i18n·API 클라이언트(D)를 함께 개발한다.
세 앱이 같은 디자인 토큰과 타입을 공유해야 하며, 지원 대상 회사(더게임)의 JD가
"pnpm workspace 기반 모노레포로의 점진적 통합"을 명시하고 있어 동일한 환경에서의
역량 증명이 필요하다.

## 결정 (Decision)

pnpm workspace로 단일 저장소를 구성하고, `apps/*`(배포 단위)와
`packages/*`(공유 라이브러리)로 분리한다. 태스크 오케스트레이션(빌드 캐시,
의존 순서)은 Turborepo를 사용한다.

## 검토한 대안 (Alternatives)

| 대안 | 장점 | 단점 | 탈락 사유 |
|------|------|------|-----------|
| 저장소 분리(polyrepo) | 앱별 독립 배포·권한 단순 | 디자인 시스템 공유 시 배포 파이프라인 필요, 타입 동기화 비용 | 1인 개발에서 공유 코드 오버헤드가 이득을 압도 |
| npm/yarn workspace | 추가 도구 불필요 | phantom dependency 허용, 디스크 사용량 큼 | pnpm의 엄격한 의존성 격리가 모노레포 안정성에 유리, JD 스택과도 일치 |
| Nx | 강력한 캐시·그래프 분석 | 러닝커브와 설정 복잡도 | 4개 워크스페이스 규모에 과함. Turborepo로 충분 |

## 결과 (Consequences)

- (+) 디자인 시스템·타입·i18n 리소스를 버전 배포 없이 즉시 공유
- (+) 단일 lockfile로 의존성 버전 일관성 확보
- (+) 리뷰어가 저장소 하나로 전체 구조를 파악 가능
- (−) React Native(Expo) 앱은 모노레포에서 Metro 번들러 설정(심볼릭 링크 해석)이
  추가로 필요 → [0002]에서 다룸
- (−) CI가 전체 워크스페이스를 인지해야 하므로 파이프라인 설정이 단일 앱보다 복잡
