# 002. product 홈페이지 초기 로딩 (Lighthouse 모바일)

> S09. 대상: `apps/product`의 랜딩(`/ko`)과 문의 페이지(`/ko/contact`).

## 증상 / 문제

잠재 고객·채용 리뷰어가 처음 보는 화면이 마케팅 페이지다. 눈에 띄게 느리진 않았지만
**측정된 적이 없었다**. 특히 두 가지가 의심스러웠다.

- 전역 레이아웃이 웹폰트 CSS 두 개(jsDelivr의 Pretendard 동적 서브셋,
  Google Fonts의 IBM Plex Mono)를 `<head>`에서 **동기 로드**한다 → 렌더 차단 의심.
- 히어로의 `CaptionStage`가 한 글자씩 타이핑되며 자라는 자막 박스다 → CLS 의심.

## 측정

- 도구: Lighthouse 12.8.2 CLI, Chromium 140 (playwright 캐시 바이너리).
- 조건: **모바일 프리셋 기본값** — 화면 412×823(DPR 1.75), Slow 4G 시뮬레이션
  (RTT 150ms / 1,638kbps), **CPU 4× 스로틀**, `throttlingMethod: simulate`.
- 절차: 프로덕션 빌드 산출물을 정적 서버로 서빙 → 페이지당 **3회 실행, 중앙값**.
- 지표: Performance 점수, FCP, LCP, CLS, TBT.

### 재현 방법

`next.config.ts`가 `output: 'export'`이므로 `next start`는 동작하지 않는다
(Next가 명시적으로 거부한다). 대신 export 산출물을 gzip·캐시 헤더까지 흉내내는
최소 정적 서버로 서빙했다.

```bash
pnpm --filter @thegame/product build
node apps/product/scripts/serve-static.mjs apps/product/out 3021

CHROME_PATH=/home/hyun/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome \
pnpm dlx lighthouse@12 http://localhost:3021/ko \
  --only-categories=performance --output=json --output-path=./lh.json --quiet \
  --chrome-flags="--headless=new --no-sandbox --disable-gpu --disable-dev-shm-usage"
```

### 기준선 (개선 전, 3회 중앙값)

| 페이지 | Performance | FCP | LCP | CLS | TBT |
|---|---|---|---|---|---|
| `/ko` (랜딩) | **99** | 1.54s | **2.02s** | **0.028** | 10ms |
| `/ko/contact` | **98** | 1.74s | **2.10s** | 0.001 | 43ms |

3회 원시값 (`/ko`): 93 / 99 / 99 — 첫 회는 서드파티 폰트 CDN 콜드 커넥션 때문에
튄다. 이 변동성 자체가 아래 원인 분석의 단서였다.

## 원인 분석

### 1. LCP의 78%가 "렌더 대기"였다

LCP 요소는 히어로의 `<h1>`. Lighthouse의 LCP 단계 분해:

| 단계 | 시간 | 비중 |
|---|---|---|
| TTFB | 452ms | 22% |
| Load Delay / Load Time | 0ms | 0% |
| **Render Delay** | **1,569ms** | **78%** |

텍스트라 다운로드 비용이 0인데도 1.5초를 기다린다 → 렌더 차단 자원 문제.
`render-blocking-resources` 감사 결과:

| 자원 | 차단 |
|---|---|
| `fonts.googleapis.com/css2?family=IBM+Plex+Mono...` | 894ms |
| `cdn.jsdelivr.net/.../pretendardvariable-dynamic-subset.min.css` | 942ms |
| 앱 자체 CSS 3개 (합계 4.6KB) | 757ms |

서드파티 폰트 CSS 두 개가 차단 시간의 대부분을 차지한다. 자체 CSS는 이미 작다.

### 2. 한국어 페이지에서 폰트만 390KB

`network-requests` 감사: 총 전송량 546KB 중 **jsDelivr에서만 390KB**.
Pretendard 동적 서브셋은 한글을 `unicode-range`로 쪼갠 파일이라, 한국어 랜딩 페이지가
**woff2 서브셋 15개**를 끌어온다. 게다가 jsDelivr에 `preconnect`가 없어 연결 수립에
243ms를 더 쓴다(`uses-rel-preconnect`).

### 3. CLS 0.028의 출처는 타이핑 자막이었다

`layout-shifts` 감사가 지목한 노드:

| 노드 | 기여 |
|---|---|
| `span.CaptionStage_cursor` (`▌`) | 0.0135 + 0.0014 |
| `section#symposia` (아래 콘텐츠 밀림) | 0.0024 |
| 히어로 CTA 버튼 (웹폰트 swap) | 0.0006 |

원인은 두 가지다. (a) 자막이 확정되면 커서 `▌`를 **DOM에서 제거**해 인라인 폭이
줄고, (b) 타이핑이 진행되며 문장이 줄바꿈을 넘길 때 `.source`의 `min-height: 2.6em`
예약분을 넘어선다. 둘 다 자막 박스 아래 전체를 밀어 올린다.

### 4. TBT는 문제가 아니었다

`CaptionStage`의 55ms 간격 타이핑 리렌더가 TBT를 먹을 것으로 의심했으나,
측정값은 랜딩 **10ms** / 문의 43ms로 200ms 예산 대비 여유가 크다.
메인 스레드 총 작업 909ms, 스크립트 부팅 307ms, 롱태스크는 문서 파싱 118ms와
React 청크 66ms 두 건뿐이다. → **애니메이션 지연 시작/경량화는 하지 않는다.**
근거 없는 최적화를 넣지 않는 것도 결정이다.

### 5. 번들은 이미 서버 컴포넌트 중심이었다

`next build` 기준 랜딩 First Load JS 106KB (공유 102KB + 페이지 3.6KB).
클라이언트 컴포넌트는 `CaptionStage`(핵심 연출), `SiteHeader`(경로 기반 언어 전환),
`ContactForm`(폼 상태), `SetLang` 넷뿐이고 랜딩 본문·카드·푸터는 모두 서버 컴포넌트다.
줄일 여지는 `SetLang`(아래 개선 3)뿐이었다.

## 개선

측정에서 나온 것만 손댔다. 순서대로, 각 단계마다 다시 쟀다.

### 개선 1 — 모노 폰트를 `next/font`로 자체 호스팅

`fonts.googleapis.com`의 CSS를 런타임에 부르면 오리진이 하나 더 붙고 렌더가 894ms
막힌다. `next/font/google`은 빌드 시점에 woff2를 받아 앱 도메인에서 서빙하고
@font-face를 앱 CSS에 인라인하며 폰트를 preload한다 (`src/fonts.ts`).
`.mono` 규칙은 `var(--tg-font-mono-web)`을 먼저 보게 바꿨다.

### 개선 2 — 한글 웹폰트를 임계 경로에서 뺐다 (트레이드오프)

> **이 판단은 아래 [3차](#3차-브랜드-서체-복귀--서브셋-자체-호스팅)에서 뒤집혔다.**
> "브랜드 서체는 무겁다"는 전제가 틀렸다 — 쓰는 글자만 서브셋하면 81KB다.


먼저 **비동기 로드**를 시도했다 — `media="print"` → onload에서 `all`로 바꾸는 표준
패턴. FCP는 1.54s → 0.90s로 크게 좋아졌지만 **LCP는 2.02s → 2.07s로 그대로**였다.
이유는 측정에 다 나와 있었다.

- 첫 페인트는 폴백 폰트로 즉시 나오지만, 390KB의 서브셋이 뒤늦게 도착해 **폰트가 교체되는
  순간 히어로 `<h1>`이 다시 그려진다**. 크롬은 이 재페인트를 새 LCP 후보로 기록한다.
- 즉 이 폰트가 첫 화면에 관여하는 한, **첫 페인트를 막든(=느린 FCP) 나중에 교체하든(=늦은 LCP)**
  둘 중 하나를 낸다.

그래서 **한글 웹폰트를 쓰지 않기로** 했다. 디자인 토큰의 `--tg-font-sans`가 이미
`Pretendard Variable → Pretendard → -apple-system → … → Apple SD Gothic Neo → Noto Sans KR`
순서를 선언하고 있어, 폰트가 로컬에 있으면 그대로 쓰이고 없으면 OS 한글 UI 폰트로 렌더된다.

| | 유지 (동기) | 비동기 로드 | 제거 (채택) |
|---|---|---|---|
| 전송량 (`/ko`) | 546KB | 546KB | **158KB** |
| 요청 수 | 30 | 30 | **15** |
| 서드파티 바이트 | 412KB | 412KB | **0** |
| FCP | 1.54s | 0.90s | **0.90s** |
| LCP | 2.02s | 2.07s | **1.91s** |

**트레이드오프**: 브랜드 서체를 잃는다. 되돌리려면 `DocumentHead`에 링크 한 줄이면 되고,
서체를 꼭 유지해야 한다면 다음 단계는 **실제 사용 글자만 서브셋해 자체 호스팅**하는 것이다
(모노 폰트처럼 `next/font/local`). 지금은 근거 있는 158KB 쪽을 택했다.

### 개선 3 — 자막 박스의 치수를 처음부터 확정 (CLS)

두 가지를 고쳤다 (`CaptionStage`).

1. **커서를 폭 0 앵커 안에 절대배치**했다. 기존에는 `▌`가 타이핑 경계에 **끼어 있어서**
   한 글자 진행될 때마다 뒤쪽 텍스트 전체가 밀렸고, 확정 시점에는 커서가 DOM에서
   사라지며 한 번 더 밀렸다. 이제 커서는 레이아웃에 폭을 기여하지 않는다.
2. **문장 3개를 같은 그리드 칸에 겹쳐 쌓고** 현재 것만 보이게 했다. 박스 높이가 항상
   "가장 긴 문장" 기준으로 고정되므로 문장 전환·번역 등장에서도 아래가 밀리지 않는다.
   아직 타이핑되지 않은 뒷부분은 `opacity: 0`으로 깔아 줄 수까지 미리 확정한다.

단계별로 쟀다. **겹쳐 쌓기만 넣었을 때는 0.028 → 0.025로 거의 그대로**였고,
커서를 폭 0 앵커로 빼내자 **0.001**로 떨어졌다. 즉 지배적인 원인은 매 글자마다 뒤 텍스트를
밀어내던 커서였다.

**CLS의 주범은 웹폰트가 아니었다** — 웹폰트를 완전히 제거한 빌드에서도 커서 수정 전에는
0.028이 그대로 나왔다. 폰트 교체가 만든 시프트는 히어로 CTA 버튼의 0.0007뿐이었다.

### 하지 않은 것

- **애니메이션 지연 시작/경량화**: 기준선 TBT가 10ms라 근거가 없었다 (위 원인 분석 4).
- **클라이언트 컴포넌트 축소**: 랜딩은 이미 서버 컴포넌트 중심이었다 (원인 분석 5).
  다만 SEO 작업(S11)에서 `<html lang>`을 정적 HTML에 박기 위해 루트 레이아웃을 둘로 나누며
  클라이언트 컴포넌트 `SetLang`은 사라졌다.
- **앱 자체 CSS 인라인**: 남은 렌더 차단은 CSS 3개(4.6KB)뿐이고 개선 후 차단 시간은
  821ms → 157ms로 이미 줄었다.

### TBT가 올라간 이유

숨기지 않고 적는다. 두 가지가 겹쳤다.

1. **TBT 창이 앞으로 당겨졌다.** TBT는 FCP 이후의 롱태스크만 센다. FCP가 640ms 빨라졌으니
   예전에는 FCP *이전*에 끝나 집계되지 않던 하이드레이션 작업이 이제 창 안으로 들어온다.
2. **자막 레이어가 3배가 됐다.** 겹쳐 쌓기로 DOM이 늘어 스크립트 평가가
   313ms → 427ms(4× 스로틀 기준, 실측 약 +28ms)로 늘었다.

CLS를 0.028 → 0.001로 줄이기 위해 치른 값이고, TBT 55~62ms는 좋은 임계값(200ms)의
1/3 수준이라 Performance 점수는 오히려 100으로 올랐다. 그대로 둔다.

### LCP가 5%밖에 안 줄어든 이유

Lighthouse의 **시뮬레이션** LCP는 실측 페인트 시각이 아니라, LCP 요소에 영향을 줄 수 있는
자원 그래프(렌더 차단 CSS + 스크립트 다운로드·평가)를 스로틀 조건에 대입해 계산한다.
실측(`observedLargestContentfulPaint`)은 개선 전 325ms → 개선 후 122ms이고 두 경우 모두
**LCP == FCP**다 — 즉 히어로 `<h1>`은 첫 페인트에 이미 그려진다. 시뮬레이션 LCP를 더
낮추려면 공유 청크(First Load JS 102KB — React + Next 런타임)를 줄여야 하는데, 이건 프레임워크
바닥값이라 이 앱 코드에서 손댈 여지가 없다. **여기가 현재 구조의 상한이다.**

## 3차: 브랜드 서체 복귀 — 서브셋 자체 호스팅

2차에서 한글 브랜드 서체(Pretendard)를 아예 싣지 않는 선택을 했는데, 그건 **성능 수치만 보고
디자인 자산을 버린 것**이었다. 다시 재보고 판단했다.

### 크기 실측 (무엇을 실어야 하는가)

| 방식 | 크기 | 요청 |
|---|---|---|
| Pretendard Variable 전체 | 2,009 KB | 1 |
| 현대 한글 11,172자 서브셋 | 1,695 KB | 1 |
| jsDelivr 동적 서브셋 (2차에서 제거한 것) | **390 KB** | **15 (외부 오리진)** |
| **렌더되는 글자만 서브셋 (355자)** | **81 KB** | **1 (동일 출처)** |

한글은 음절이 많아 "전체 서브셋"이 의미가 없다(2,009 → 1,695KB). 반면 이 사이트가 실제로
쓰는 글자는 355자뿐이라 **81KB, 96% 감소**다. 제거 전에 브라우저가 실제로 받던 양(390KB /
15요청 / 외부 오리진)보다도 4.8배 작다. 그래서 "브랜드 서체 = 무겁다"는 전제 자체가 틀렸다.

생성: `pnpm --filter @thegame/product font:subset` (`scripts/subset-brand-font.mjs`) —
빌드 산출물 HTML에서 렌더되는 글자를 모아 서브셋하고, 폰트와 **글자 목록(charset)**을 함께
커밋한다.

### 재측정 (동일 조건: 모바일 프리셋, Slow 4G / 4× CPU, 3회 중앙값)

| 페이지 | 지표 | 2차 (서체 없음) | 3차 (서브셋 서체) |
|---|---|---|---|
| `/ko` | Performance | 100 | **98** |
| | FCP | 0.90s | 0.90s |
| | LCP | 1.91s | **2.40s** |
| | CLS | 0.001 | 0.001 |
| | TBT | 55ms | 45ms |
| | 전송량 / 요청 | 158KB / 15 | 236KB / 16 |
| `/ko/contact` | Performance | 100 | 97 |
| | LCP | 1.92s | 2.41s |

### 이 트레이드오프를 받아들인 근거

- **실측 LCP는 100ms다.** `observedLargestContentfulPaint` = 100ms로 2차와 차이가 없다.
  2.40s는 Lighthouse가 Slow 4G(1.6Mbps)를 대입해 계산한 **시뮬레이션 값**이고, preload된
  81KB 폰트가 히어로 `<h1>`의 자원 그래프에 들어가서 생기는 페널티다.
- **2.40s는 여전히 Core Web Vitals "좋음"(<2.5s) 안이다.** 점수 2점을 브랜드 타이포그래피와
  맞바꾼 것이다. 프론트엔드 포지션 데모에서 시스템 폰트로 떨어진 한글 랜딩은
  윈도우(맑은 고딕)와 맥(Apple SD Gothic Neo)에서 서로 다르게 보인다.
- `font-display: optional`도 재봤으나 **수치가 동일**했고(98 / LCP 2.40s), 대신 느린 회선의
  첫 방문에서 서체가 아예 적용되지 않는다. 그래서 `swap`을 택했다. `adjustFontFallback: false`
  로 Next의 자동 폴백 메트릭을 끄고 토큰의 폴백 체인을 쓰며, 이 조합에서 CLS는 0.001이다.

### 남은 개선 여지 (하지 않음)

히어로 위쪽 글자만 담은 초경량 서브셋을 preload하고 나머지를 지연 로드하면 시뮬레이션 LCP를
더 낮출 수 있다. 폰트 파일이 둘로 갈리고 글자 분할 규칙을 유지해야 하는 복잡도에 비해
얻는 게 점수 2점이라 하지 않았다.

## 회귀 방지

- `apps/product`에 vitest 테스트를 추가해 빌드 산출물을 검사한다 (`src/__tests__/build-output.test.ts`) —
  `sitemap.xml`·`robots.txt` 존재, 페이지별 title/description/OG/hreflang/JSON-LD,
  그리고 **HTML에 서드파티 스타일시트·폰트 링크가 없을 것**. 폰트 CDN이 다시 들어오면 실패한다.
- **서체 서브셋 커버리지 테스트** (`src/__tests__/brand-font.test.ts`) — 렌더되는 모든 글자가
  서브셋에 들어 있는지 검사한다. 서브셋은 "쓰는 글자만" 담으므로 카피를 추가하고 서브셋을 다시
  만들지 않으면 **그 글자만 시스템 폰트로 떨어지는** 조용한 결함이 생긴다. 이걸 CI가 막는다.
  파일 크기 상한(150KB)도 함께 검사해 전체 폰트가 커밋되는 회귀를 잡는다.
- (미적용) Lighthouse CI를 S10 워크플로에 붙여 LCP < 2.5s / CLS < 0.1 예산을 거는 것은
  S10 담당 범위라 여기서는 하지 않았다.
