# 001. 자막 스트림 수신 시 리스트 전체 리렌더 제거

> S08. 대상: `apps/live-demo`의 Symposia 자막 화면(`SymposiaScreen`)과 운영 콘솔의
> 자막 모니터(`CaptionMonitor`). 성능 축은 **런타임 갱신 비용**이다
> (S09/002는 홈페이지 초기 로딩 — 대상 앱도 지표도 다르다).

## 증상 / 문제

부분 자막은 단어 단위로 갱신된다. 목 서버 기준 문장 하나에 4~6회, 40분 강연이면
수백 회의 상태 업데이트가 쏟아진다. `captionStore`는 이벤트 1건마다 `entries` **배열을
통째로 교체**하고, 화면은 그 배열을 그대로 `FlatList`의 `data`로 넘긴다. `CaptionRow`는
memo되어 있지 않다. 즉 **한 단어가 늘어날 때마다 화면에 떠 있는 자막 줄 전부가 다시
렌더될 가능성**이 있었다. 저사양 폰에서 장시간 시청 시 프레임 드랍·발열로 이어지는 부류다.

"가능성"이라고 쓴 이유는 측정한 적이 없어서다. 그래서 고치기 전에 먼저 쟀다.

## 측정

- 도구: **React 프로파일링 빌드 + 자체 계측기**(`apps/live-demo/scripts/perf-caption*.js`),
  헤드리스 Chromium 140(playwright 캐시 바이너리)을 CDP로 제어.
- 조건: 모바일 뷰포트 412×823(DPR 1.75), **CPU 4× 스로틀**, 목 서버 SSE 실시간 재생
  (`rate: 2`), 프로덕션 웹 번들(`expo export`, `NODE_ENV=production`).
  시나리오마다 **3회 실행, 중앙값**. (컴포넌트 수는 같은 이벤트열에 대해 결정적이라 3회가
  자릿수까지 같았고, 시간만 흔들렸다.)
- 기록 항목(명세): **부분 자막 이벤트 1회당 커밋에 포함된 컴포넌트 수**와 **커밋 시간 분포**.

### 왜 DevTools 확장 대신 자체 계측기인가

React DevTools Profiler는 확장 프로그램 UI를 거쳐야 해서 헤드리스 재현이 어렵고,
"이 커밋에 몇 개의 컴포넌트가 들어갔나"를 숫자로 뽑아 저장하기도 번거롭다. 대신
**DevTools가 쓰는 것과 같은 자리·같은 판정 기준**을 직접 썼다.

- `__REACT_DEVTOOLS_GLOBAL_HOOK__` 자리에 계측용 훅을 꽂아 `onCommitFiberRoot`로 커밋을 받는다.
  주입은 페이지의 어떤 스크립트보다 먼저다(`Page.addScriptToEvaluateOnNewDocument`).
- "이번 커밋에서 렌더됐다"의 판정은 DevTools와 같은 **`PerformedWork` 플래그**다.
  memo로 걸러진 컴포넌트는 파이버를 방문해도 이 플래그가 서지 않는다.
- 커밋 시간은 루트 파이버의 **`actualDuration`** — DevTools 프로파일러가 커밋 시간으로
  쓰는 바로 그 값이다. 이 값은 프로파일링 빌드에서만 기록되므로 `PROFILE_REACT=1`로
  react-dom을 `react-dom/profiling`으로 바꿔 빌드한다(`metro.config.js`, 기본 빌드는 무영향).

계측기가 틀리기 쉬운 지점이 하나 있어서 적어 둔다. **통째로 bailout된 서브트리는 파이버
객체가 재사용되므로 `flags`에 지난 커밋의 `PerformedWork`가 남아 있다.** 트리를 그냥 훑으면
memo 효과가 통계에서 사라진다(첫 시도에서 실제로 그랬다 — 커밋 시간이 0.3ms인데 컴포넌트
258개가 렌더된 것으로 집계됐다). DevTools와 같은 규칙으로,
`fiber.child === fiber.alternate.child`면 그 아래는 이번에 렌더되지 않은 것으로 보고
내려가지 않는다. 이 규칙을 넣은 뒤 **하트비트 이벤트의 커밋이 컴포넌트 0개 / 0ms**로
찍혔다 — 계측기가 bailout을 제대로 보고 있다는 자기 검증이다.

### 재현 방법

```bash
# 1. 프로파일링 웹 번들 (측정 전용 — 기본 빌드는 이 스위치가 없으면 그대로다)
PROFILE_REACT=1 EXPO_PUBLIC_API_URL=http://localhost:4021 \
  pnpm --filter @thegame/live-demo exec expo export --platform web \
  --output-dir dist-profile --no-minify

# 2. 측정 (목 서버·정적 서버·크로미움을 하네스가 직접 띄우고 정리한다)
pnpm --filter @thegame/mock-server exec tsx \
  ../live-demo/scripts/perf-caption.mjs --label before-40 --sentences 40 --rate 2

# 3. 원자료에서 요약만 다시 계산 (측정을 다시 돌리지 않는다)
pnpm --filter @thegame/mock-server exec tsx \
  ../live-demo/scripts/perf-caption.mjs --from perf-caption-before-40.json
```

`--no-minify`는 컴포넌트 이름을 살리기 위해서다(민파이되면 `CaptionRow`가 한 글자로 바뀌어
"무엇이 렌더됐는지"를 못 적는다). 번들은 여전히 `NODE_ENV=production`이다.

**시나리오 두 개**를 잰다.

| | 문장 | 클라이언트가 받는 부분 자막 | 확정 자막(서버 발행 / 클라이언트 수신) |
|---|---|---|---|
| A. 배포 픽스처 그대로 | 10 | 46회 | 40건 / 20건 |
| B. 명세 조건(자막 40+건) | 40 | 184회 | 160건 / 80건 |

명세는 "확정 자막 40+건, 부분 갱신 수백 회"를 조건으로 잡았는데, **현재 keynote 픽스처는
10문장**이다. 서버가 발행하는 확정 이벤트는 40건(문장 10 × 원문+3언어)이지만 참가자
한 명이 실제로 받는 것은 `lang` 필터를 거쳐 20건이고 자막 줄은 10줄이다. 그래서
목 서버 소스는 손대지 않고 하네스가 `createMockServer({ session: { template } })`에
문장을 순환 복제한 스크립트를 넣어 40문장 세션을 만든다(시나리오 B). 시나리오 A는
템플릿 그대로라 **배포된 목 서버와 동작이 같다**.

### 기준선 (개선 전, 3회 중앙값)

부분 자막 이벤트 **1회당** — 그 이벤트가 낳은 모든 커밋을 합친 값이다.

| 시나리오 | 렌더된 컴포넌트 (평균/p50/p95/최대) | 렌더 시간 ms (평균/p95/최대) | 이벤트당 커밋 |
|---|---|---|---|
| A (10문장) | **116.5** / 113 / 203 / 239 | **4.87** / 7.70 / 12.50 | 2.30 |
| B (40문장) | **279.9** / 261 / 611 / 773 | **6.68** / 12.40 / 16.00 | 2.55 |

확정 자막 이벤트 1회당 (참고): A **105.5개 / 4.68ms**, B **240.5개 / 6.17ms**.

세션 전체 렌더 시간 합계: A **434.8ms** (커밋 161건) / B **1,830.4ms** (커밋 731건).

## 원인 분석

### 1. 부분 자막 1건이 화면에 떠 있는 자막 줄 **전부**를 다시 그린다

부분 자막 이벤트의 첫 커밋에서, 커밋에 들어간 `CaptionRow` 수와 그 시점에 마운트돼 있던
`CaptionRow` 수가 **정확히 같다**.

| 시나리오 | 첫 커밋의 렌더된 줄 / 마운트된 줄 |
|---|---|
| A (10문장) | 5.63 / 5.63 |
| B (40문장) | **20.47 / 20.47** |

하나도 걸러지지 않는다. 그래서 이벤트당 비용이 자막 개수에 그대로 비례한다.

| 마운트된 자막 줄 | 부분 자막 이벤트 1회당 컴포넌트 | 이벤트 1회당 렌더 시간 |
|---|---|---|
| 0–7 | 99.8 | 4.76ms |
| 8–15 | 185.1 | 5.45ms |
| 16–23 | 270.5 | 6.65ms |
| 24–31 | 358.6 | 7.59ms |
| 32–39 | **446.6** | **8.48ms** |

자막 줄 하나당 약 **11개**다 — 줄 하나는 `CellRenderer` + `VirtualizedListCellContextProvider`
+ `CaptionRow` + `View` + `Text`×2(+ react-native-web이 `Text`마다 다는 `LocaleProvider`×2)로
이뤄진다.

원인은 둘이 겹쳐 있다.
- `upsertEntry`가 부분 자막마다 `entries` 배열을 새로 만든다 → `FlatList`의 `data`
  참조가 바뀐다 → `VirtualizedList`가 리렌더되고 **모든 셀이 따라 렌더된다**
  (`CellRenderer`는 `React.Component`이고 `shouldComponentUpdate`가 없다).
- `CaptionRow`가 memo되어 있지 않아 셀이 렌더되면 줄도 무조건 다시 렌더된다.

**FlatList의 가상화 자체는 일하고 있다.** 자막 40줄 세션에서 마운트된 줄은 평균 21줄이다.
문제는 "몇 줄이 떠 있느냐"가 아니라 "떠 있는 줄이 매 단어마다 전부 다시 그려지느냐"다.

### 2. 화면 껍데기까지 매 단어마다 다시 렌더된다

부분 자막 이벤트 1건당 `SymposiaScreen`이 **정확히 1회** 렌더된다(184 이벤트 → 184회).
`SymposiaScreen`이 `entries`를 구독하는데 그 배열이 단어마다 바뀌기 때문이다. 그래서
언어 칩·스테이지 토글·글꼴 버튼(`Pressable` 12개)과 `ConnectionBadge`, `StatusBar`가
자막 내용과 무관하게 매번 다시 렌더된다.

### 3. 이벤트 1건이 커밋 2~3건을 만든다 (뒤 커밋은 싸다)

부분 자막 이벤트당 커밋은 2.30~2.55건이다. 첫 커밋이 무겁고(B 기준 평균 238.7개 / 5.81ms),
후속 커밋은 대부분 비어 있다(평균 26.5개 / 0.56ms, 286건 중 246건이 컴포넌트 0개).
후속 커밋은 자동 스크롤(`onContentSizeChange` → `scrollToEnd`)이 만드는 `VirtualizedList`
내부 상태 갱신이다. **렌더 시간의 87%가 첫 커밋**이므로 여기서는 손대지 않는다.

### 4. 가설 2("셀렉터가 넓어 무관한 상태 변화에도 화면이 갱신된다")는 **틀렸다**

`captionStore`의 하트비트 이벤트는 `set({})`으로 스토어 알림을 발생시킨다. 스토어
알림 → React 커밋까지는 실제로 일어난다. 그러나 **그 커밋에서 렌더된 컴포넌트는 0개,
렌더 시간은 사실상 0**이다(시나리오 B에서 하트비트 4건 → 커밋 4건, 컴포넌트 0개, 합계 0.0~0.2ms).
화면의 셀렉터(`state.status` / `state.session` / `state.entries` / `state.ended`)는 이미
필드 단위로 쪼개져 있어서, 값이 그대로면 `useSyncExternalStore`가 리렌더를 막는다.

즉 **셀렉터를 더 잘게 쪼개서 얻을 것은 없다** — 이 항목은 개선하지 않는다.
(가설 2가 겨냥한 비용은 실은 원인 2다: 셀렉터가 넓은 게 아니라, **화면이 구독하는 값
자체가 단어마다 바뀐다**. 고칠 자리는 셀렉터가 아니라 스토어의 모양이다.)

## 개선

측정이 지목한 것만 고쳤다. 셋 다 원인 1·2에 직접 대응한다.

### 개선 1 — 진행 중 부분 자막을 리스트에서 분리 (스토어)

`captionStore`를 둘로 나눴다.

```ts
entries: CaptionEntry[]      // 자막 히스토리 — 확정 이벤트에만 바뀐다
partial: CaptionEntry | null // 진행 중인 원문 한 줄 — 단어마다 바뀐다
```

부분 자막 이벤트는 이제 `partial`만 갈아끼우고 **`entries` 참조는 건드리지 않는다**.
`FlatList`의 `data`가 그대로이므로 리스트는 아예 리렌더 대상이 아니다.

번역만 먼저 도착해 원문이 없는 항목(재연결 복구 창 밖의 자막)은 예전처럼 `entries`에
자리표시자로 들어가고, 진행 중인 문장의 번역은 확정될 때 이어받는다 — 표시 규칙은 그대로다.

### 개선 2 — 진행 중 자막을 스스로 구독하는 잎 컴포넌트로 (화면)

부분 자막을 화면이 구독하면 원인 2가 그대로 남는다. 그래서 `LiveCaptionLine`(리스트 모드)과
`LiveStageCaption`(스테이지 모드)이 **자기 자신만** 스토어의 `partial`을 구독한다.
`SymposiaScreen`은 이제 `entries`만 보므로 부분 자막에는 렌더되지 않는다. 콘솔의
`CaptionMonitor`는 "진행 중 자막이 **있는지**"(`partial !== null`)만 구독한다 — 문장당 2회만
바뀌는 값이라 단어마다 모니터가 리렌더되지 않으면서 "대기 중" 안내를 제때 치울 수 있다.

UI도 같이 정리됐다. 진행 중 문장이 리스트의 마지막 줄이 아니라 리스트 아래 **고정된 한 줄**이
된다. 자막은 아래에서 위로 쌓이게(`flexGrow` + `justifyContent: 'flex-end'`) 바꿔 진행 중인 줄과
붙어 있게 했다. 지나간 자막을 스크롤해 훑는 동안에도 "지금 말하고 있는 문장"이 화면에 남고,
자동 스크롤이 단어마다 리스트를 밀어 올리지 않는다. 단어마다 갱신되는 줄이라 스크린리더
라이브 리전으로는 두지 않았다(확정 자막을 훑는 것 자체가 불가능해진다).

### 개선 3 — `CaptionRow` memo화 + 안정적 key

확정 자막이 들어오면 `entries`는 여전히 새 배열이 되고, 그때는 모든 셀이 렌더된다.
`CaptionRow`를 `memo`로 감싸 **내용이 바뀐 줄만** 실제로 렌더되게 했다.
스토어가 바뀐 항목만 새 객체로 만들기 때문에 props 동등성이 성립한다.
`keyExtractor`는 이미 자막 id였다(그대로). `renderItem`은 `useCallback`으로 고정했다.

### 하지 않은 것

- **셀렉터 세분화**: 원인 분석 4 — 근거가 없다.
- **가상화 튜닝**: 40문장 세션에서 마운트된 줄은 평균 21줄이었다. `FlatList` 기본값으로 충분하다.
- **자동 스크롤이 만드는 후속 커밋 제거**: 렌더 시간의 13%다(원인 분석 3).

**컴포넌트 6개**는 `LiveCaptionLine` + `CaptionRow` + `View`×2 + `Text` + `LocaleProvider`,
즉 "진행 중인 자막 한 줄" 그 자체다. 그리고 자막이 몇 줄이든 값이 같다.

| 마운트된 자막 줄 | before: 컴포넌트/이벤트 | after: 컴포넌트/이벤트 |
|---|---|---|
| 0–7 | 99.8 | **6.0** |
| 8–15 | 185.1 | **6.0** |
| 16–23 | 270.5 | **6.0** |
| 24–31 | 358.6 | **6.0** |
| 32–39 | 446.6 | **6.0** |

자막 줄 수에 대한 기울기는 **약 11 → 0.0**이다. 커밋 규모가 자막 개수와 무관해졌다(완성 기준 2).

숨기지 않고 적는다. **확정 자막 1건은 조금 더 비싸졌다.** 이유는 일이 옮겨갔기 때문이다.
예전에는 문장의 첫 단어가 도착할 때 줄이 리스트에 **마운트**되고 확정 시점에는 갱신만
됐는데, 이제는 확정 시점에 줄이 새로 마운트된다. 자동 스크롤과 진행 줄 해제까지 겹쳐
확정 이벤트당 커밋이 3.0 → 4.3건이 됐다. memo는 제 몫을 하고 있다 — 확정 이벤트마다
셀 30개가 다시 렌더되지만 실제로 렌더되는 `CaptionRow`는 **1개**뿐이다. 남은 158개는
셀 껍데기(`CellRenderer` + 컨텍스트 + `View`)와 화면 껍데기이고, 이건 `FlatList` 구조의
값이지 자막 줄의 값이 아니다.

## 회귀 방지

- **스토어 유닛 테스트** (`src/stores/__tests__/captionStore.test.ts`) — 리렌더의 원인을
  스토어 레벨에서 못박는다.
  - 부분 자막 이벤트를 50건 처리해도 **`entries` 참조가 불변**이다(핵심 계약).
  - 확정 자막이 들어오면 그때만 `entries`가 새 배열이 되고, **바뀌지 않은 항목의 객체
    참조는 그대로**다 → memo된 `CaptionRow`의 props 동등성이 성립한다.
  - 번역 선도착·재연결 복구·세션 재시작 등 기존 표시 규칙이 유지되는지도 함께 본다.
- **memo·props 안정성 테스트** (`src/components/__tests__/captionRow.test.ts`) —
  `CaptionRow`가 memo 컴포넌트인지, 그리고 스토어가 실제로 내보내는 연속 상태에서
  React의 기본 비교로 props가 같게 나오는지 검사한다. memo를 벗기거나 스토어가 매번 새
  객체를 만들면 실패한다. (RN 컴포넌트 렌더 테스트는 여전히 범위 밖이라 모듈 형태만 본다.)
- 측정 자체는 CI에 걸지 않았다. 헤드리스 크로미움 + 프로파일링 빌드가 필요하고 시간 수치가
  머신 부하에 따라 흔들려서, 예산(budget)으로 쓰기엔 임계값을 정직하게 정할 수 없다.
  대신 위 두 테스트가 **리렌더를 만드는 구조적 조건**(참조 불변 + memo)을 지킨다.
