# S08. perf: 자막 스트림 리렌더 측정·개선

- **갈래**: 성능 · **의존**: S01–S04 (화면 재편 후 측정해야 유효) · **판정**: 대기

## 배경

**대상: live-demo의 런타임 렌더링 성능.** 부분 자막은 단어 단위로 갱신되므로 세션당
수백 회의 상태 업데이트가 발생한다. `captionStore`가 배열을 교체하는 구조라, 이벤트
1건마다 자막 리스트 전체가 리렌더될 가능성이 있다 — 저사양 폰에서 장시간 시청 시
프레임 드랍·발열로 이어지는 부류의 문제다. (S09의 Lighthouse와 대상 앱·성능 축이
다르다: 이쪽은 "떠 있는 앱이 얼마나 가볍게 갱신되나", S09는 "홈페이지가 얼마나 빨리
뜨나". 둘은 충돌하지 않으며 둘 다 수행한다.)

## 명세 — docs/perf 형식(측정 → 원인 → 개선 → 재측정) 준수

### 측정

- 도구: React DevTools Profiler (웹 빌드), 보조로 Chrome Performance.
- 조건: keynote 세션 전체 재생(확정 자막 40+건, 부분 갱신 수백 회), CPU 4× 스로틀,
  기록 항목 — 부분 자막 이벤트 1회당 커밋에 포함된 컴포넌트 수·커밋 시간 분포.
- 기준선을 `docs/perf/001-자막-리렌더.md`의 "측정" 섹션에 먼저 기록한다.

### 가설 (측정으로 확인할 것)

1. 부분 자막 갱신이 확정 자막 리스트 전체를 리렌더시킨다 (배열 교체 + 비메모 row).
2. 스토어 셀렉터가 넓어 무관한 상태 변화에도 화면이 갱신된다.

### 개선 후보 (측정 결과에 따라 선택)

- `CaptionRow` memo화 + 안정적 key(자막 id).
- **진행 중 부분 자막을 리스트에서 분리** — 확정 리스트는 확정 이벤트에만 갱신되고,
  부분 자막은 독립된 단일 노드로만 갱신.
- 셀렉터 세분화 (필요 필드만 구독).

### 재측정·기록

- 동일 조건 재측정 → before/after 수치를 perf 로그에 기록.
- 회귀 방지: 커밋 범위를 검증하는 테스트(또는 Profiler 수치 기준)를 명시.

## 완성 기준

1. `docs/perf/001`에 도구·조건·수치가 포함된 전체 사이클이 기록된다.
2. 부분 자막 이벤트 1회당 리렌더 범위가 측정 가능하게 줄었다 (목표: 커밋 컴포넌트 수가
   자막 개수와 무관해짐).

## 테스트

- 회귀 방지(자동): captionStore 유닛 테스트 — 부분 자막 이벤트 처리 후 **확정 리스트의
  참조 불변**(리렌더 원인 제거를 스토어 레벨에서 고정), memo화된 row의 props 안정성.
- 측정 재현: 측정 절차(도구 설정·스로틀·기록 항목)를 perf 문서에 스크립트/단계로 남겨
  누구나 동일 조건 재측정 가능하게.

## 범위 제외

네이티브(Hermes) 프로파일링(웹 측정으로 갈음, 구조 개선은 공통 적용), 가상화 튜닝
(FlatList 기본으로 충분한지 측정 후 판단).

## 구현 메모 (2026-09-01)

전체 사이클은 `docs/perf/001-자막-리렌더.md`에 있다. 명세와 달라진 것만 적는다.

- **도구**: React DevTools 확장 대신 **같은 훅 자리(`__REACT_DEVTOOLS_GLOBAL_HOOK__`)에
  자체 계측기**를 꽂았다. 헤드리스에서 재현 가능하고(`scripts/perf-caption.mjs` 한 번 실행),
  "커밋에 포함된 컴포넌트 수"를 DevTools와 같은 기준(`PerformedWork` 플래그)으로 세어
  파일로 남길 수 있다. 커밋 시간은 프로파일링 빌드의 `actualDuration`이다
  (`PROFILE_REACT=1`, `metro.config.js` — 기본 빌드는 영향 없음).
- **조건**: 명세의 "확정 자막 40+건, 부분 갱신 수백 회"는 현재 keynote 픽스처(10문장)로는
  나오지 않는다. 목 서버 소스를 고치지 않고, 하네스가 `createMockServer`에 문장을 순환
  복제한 40문장 스크립트를 주입해 시나리오 B로 만들었다. 배포 픽스처 그대로인 시나리오 A도
  함께 잰다. 두 시나리오 × 3회 실행, 중앙값.
- **가설 2는 틀렸다**: 셀렉터는 이미 필드 단위였고, 무관한 상태 변화(하트비트)의 커밋은
  컴포넌트 0개·0ms였다. 셀렉터 세분화는 **하지 않았다**. 실제 비용은 "화면이 구독하는 값이
  단어마다 바뀐다"였고, 고칠 자리는 셀렉터가 아니라 스토어의 모양이었다.
- **결과**: 부분 자막 이벤트 1회당 렌더 컴포넌트 279.9 → 6.0개(자막 개수와 무관, 기울기
  11 → 0), 렌더 시간 6.68 → 0.73ms. 확정 자막 1건은 오히려 조금 비싸졌다(6.17 → 6.73ms —
  줄 마운트가 부분 단계에서 확정 단계로 옮겨갔다). 문장 1개 기준으로는 43.0 → 16.8ms.
- **UI 변경**: 진행 중 자막이 리스트의 마지막 줄에서 **리스트 아래 고정된 한 줄**로 나왔고,
  자막이 아래에서 위로 쌓이도록 정렬했다. 성능 때문에 시작한 구조 변경이지만 화면 동작이
  바뀌므로 여기 적는다(스크린샷 검증: 참가자 화면 / 스테이지 모드 / 콘솔 모니터).
- **범위 밖 그대로**: 네이티브(Hermes) 프로파일링, 가상화 튜닝(마운트 줄이 평균 21줄로
  가상화가 이미 동작 중 — 손댈 근거가 없었다).
